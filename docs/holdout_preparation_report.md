## 2. 怎样理解“独立”

这是开发完成后新拟、未供训练或调参、未执行的保留测试集候选版。作者读过代码和开发资料，无法据此声称第三方独立双盲；也无法仅凭字面去重证明语义独立或模型预训练未见过内容。全部110轮保留语义裁决pending状态，需在首轮运行前由独立人员审题。

银行产品事实本来就应来自知识库；“知识在库内”不是污染。“同一个训练问题加前后缀后改称新题”则不能作为独立泛化证据。审题时需同时看最近旧问法、真实问题核心和预期答案。训练源文件三份分别2000/400/2400行，存在合并重复，不能将其相加称4800个独立训练样本。

题目示例：

| ID | 测试重点 | 判断依据 |
|---|---|---|
| H-P07 | 通知存款7万元取3万元后的留存条件 | 需要计算剩余4万元并核对最低留存条件，不能只识别产品名 |
| H-C01 | 整存整取与零存整取部分提前支取的差别 | 同时覆盖两产品条件，不能只回答一半 |

## 3. 准备过程中发现的调整点

以下是资料与代码的静态证据，不是新测试集实测成绩。本轮不修复这些点。

### P1-1：先修知识事实冲突，不能只给错误FAQ加引用

证据：

- `rag_qa/data/finance/faq/银行常见问题_自建演示数据.md:63` 对超出存款保险限额的表述容易被解读为完全不能受偿；`regulation/存款保险条例__20150501.md:20` 明确写出超限部分依法从清算财产受偿。
- 同一自建FAQ `:67` 将“大额存单（视具体产品而定）”并入不在保障范围的清单；`product/个人大额存单产品说明__20260923.md:7` 将本行该产品定义为存款类产品、一般性存款。产品类别与具体保险适用条件应依据官方条款核实，不能用含混清单作为确定结论。
- 自建FAQ `:71` / `:75` 给出临时挂失“5至7天”泛化口径；`business_rule/存款挂失服务__20260923.md:7` 为该行5日内补办正式挂失，和7日后换发存折是不同环节。

官方抽查：中行公开挂失服务页支持本地整理的5日补办规则；人民银行公开回复区分了限额偿付与超限部分清算受偿。[中国银行存款挂失服务](https://www.bankofchina.com/pbservice/pb1/200807/t20080704_769.html)、[人民银行存款保险公开回复](https://wzdt.pbc.gov.cn/eportal/ui?msgDataId=d3f5c72a0157407e97b4998676c34ef2&pageId=77c3557bd521439ea5cd869f5393ba98)。这是局部核查，未认证全部法规和产品当前有效性。原gov.cn条例URL本次403，记录在source_checks.json，不把访问失败当作已核实。

后续建议：逐条核实并修订或暂停冲突FAQ；将scope/official_url/原始版本绑定到每条FAQ；重新导入和失效缓存。先做显而易见的源资料修正，再重新冻结知识快照与受影响gold，不根据模型输出倒改标准。

### P1-2：FAQ行级地区/来源仍有缺口

证据：`business_rule/销户业务规则__20261011.md:3` 标明澳大利亚分行，但 `faq/开户销户FAQ__20261011.md:67` 起混入销户问答，FAQ注册表将整文件标为CN。`faq_to_mysql.py:23` / `:27` 只取文件级元数据复制到各条问答。

后续建议：逐条确认销户FAQ来自哪份境内或境外原文；无法证明境内适用的题目先停用或标AU/needs_review。文档级过滤无法纠正问答内容被放错文件造成的错误地区元数据。本次仅指出风险，没有断言这几条内容全部违反境内规则。

### P1-3：规则仍需理解被引用、被否定的关键词

证据：`rag_qa/core/query_classifier.py:39` / `:40` 对整个输入直接search投资/投诉正则，没有区分用户真正请求与引用、否定或文章中的词。

后续建议：在独立开发样本上增加否定、引语、公开事实咨询与实际建议请求的对比数据；设计规则作用范围与冲突优先级。不要直接把本包整句加入白名单。这里能证明的是代码缺少语境区分，误拒比例仍需首轮实际测量。

### P1-4：多轮历史已保存，但检索指代解析未显式实现

证据：`rag_qa/core/rag_system.py:90` 用当前query取资料；`:94` 在生成阶段才把history注入提示词。策略选择也只接当前query（`:46`）。

后续建议：对“它/那种/刚才那个”等先做受约束的独立问题改写，保留原问题并让新请求重新经过合规判断；严格把历史当上下文，不能当新权限。是否显著影响正确率由多轮首测确认，不能只凭存在history就宣称完善多轮理解。

### P1-5：需新增适配本包的执行器和语义评分流程

证据：`evaluation/runner.py:9` 固定cases_v2路径；`:25` 每题新建会话。旧固定decision/关键词断言不能代替本包事实支持和真实多轮语义核验。

后续建议：增加单独执行器，读取questions.jsonl，同场景保持真实history，HTTP/WS使用独立会话，保留当轮实际上下文、全部WS可见token、错误/耗时、知识和模型版本。加入gold审核门禁，未审定不得生成正式盲测成绩。此执行器本轮尚未实现。

### P2：独立评审与另一个未曝光保留集

完成独立人工审题，再运行首轮，原始结果冻结后才修复。修复后本包用于回归，另建v2未曝光测试集。新增事实审核和不同产品的复杂条件题比继续扩写大量近义问句更有价值。

## 4. 评分口径变化

- 有引用不等于事实被支持；逐项检查实际块内容。
- 免责声明不等于没有越界；推荐和隐私行为按语义评判。
- “咨询客户经理”不是拒答成功条件；公开咨询误拒单独记失败。
- 无依据、歧义、过期资料与模型错误区分，不静默删掉失败样本。
- 评分示例均为假想案例，空白人工表保持未评分。
- 数据校验器通过只表示包的完整性，不表示系统通过110题。

## 5. 建议的下一步顺序

1. 独立人工审题，优先核实资料冲突和FAQ行级适用范围，更新来源和必要标签。
2. 处理已确认的知识事实问题，按明确版本重新冻结知识快照；运行代码变更也应新冻结，避免用旧哈希伪称同一基线。
3. 新增真实HTTP/WS多轮执行器；本批云端问题和检索片段外发范围需要单独明确，之前单题授权不扩展到整包。
4. 首轮完整运行并按本标准评分，公开分层结果和失败案例。
5. 按错误分布决定是否改规则、检索、历史改写或重训BERT；不预设一定要重训。
